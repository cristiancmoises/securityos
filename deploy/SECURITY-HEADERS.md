# SecurityOS — HTTP Security Headers

This document explains how SecurityOS ships security headers across **every**
deployment model, the reasoning behind each Content-Security-Policy directive,
and how to harden further.

## Source of truth

[`scripts/securityHeaders.js`](../scripts/securityHeaders.js) is the **single
source of truth**. Everything else is generated from or mirrors it:

| Deployment | How headers are applied | Coverage |
| --- | --- | --- |
| **Node server** (`next start`, the Dockerfile default) | `next.config.js` → `headers()` reads `securityHeaders.js` | ✅ Full (incl. `frame-ancestors`, HSTS, COOP, CORP) |
| **Static export** (`next export`) behind **nginx** | [`deploy/nginx.conf`](./nginx.conf) | ✅ Full |
| **Static export** behind **Caddy** | [`deploy/Caddyfile`](./Caddyfile) | ✅ Full |
| **Netlify / Cloudflare Pages** (dumb CDN) | [`public/_headers`](../public/_headers), generated by `scripts/genHeaders.js` (runs in `build:prebuild`) | ✅ Full |
| **Any** (last-resort fallback) | `<meta http-equiv>` CSP + `<meta name="referrer">` in `pages/_document.tsx` | ⚠️ Partial — `<meta>` cannot set `frame-ancestors`, HSTS, COOP, CORP |

> **Why a `<meta>` fallback is not enough on its own:** `frame-ancestors`
> (clickjacking), `Strict-Transport-Security`, `Cross-Origin-Opener-Policy` and
> `Cross-Origin-Resource-Policy` are **ignored** inside a `<meta>` tag. If you
> serve pure static files with no header control, you get the CSP but **not**
> clickjacking/HSTS protection. Put a real host in front (nginx/Caddy/Pages).

If you edit `securityHeaders.js`, run `yarn build:headers` to regenerate
`public/_headers`, and update `nginx.conf` / `Caddyfile` to match.

## Why this CSP (verified against the code, not guessed)

| Directive | Value | Reason |
| --- | --- | --- |
| `script-src` | `'self' 'wasm-unsafe-eval' blob:` | SecurityOS's own code, the WASM emulators (v86, BoxedWine, js-dos, ffmpeg, Quake3), Monaco, Next.js hydration and styled-components all work **without** `eval`. `'wasm-unsafe-eval'` permits WASM compilation only; omitting `'unsafe-eval'` blocks the most dangerous injected-script vector. ⚠️ Three Emscripten apps that *do* call `eval`/`new Function` are disabled by default — see below. |
| `style-src` | `'self' 'unsafe-inline'` | styled-components v5 injects runtime `<style>` tags and React emits inline `style=""` attributes; v5 has no clean nonce support. |
| `worker-src` / `child-src` | `'self' blob:` | `blob:` is for v86's blob-URL worker (`libv86.js`); the clock/wallpaper workers are same-origin chunks covered by `'self'`. |
| `img-src` / `media-src` | `'self' data: blob: https:` | `data:` window-control button icons, `blob:` emulator framebuffer/screenshots/canvas exports, `https:` favicons & remote media. |
| `connect-src` | `'self' data: blob: https: wss:` | In-OS Browser/IRC fetches, IPFS gateways, and the **user-configurable Tor relay** (`wss:`). |
| `frame-src` | `'self' https: blob:` | `'self'` for the local jspaint/kiwiirc app iframes; `https:` for the in-OS Browser rendering remote sites. |
| `object-src` | `'none'` | No plugins. |
| `base-uri` / `form-action` | `'self'` | Block `<base>` hijacking and off-site form posts. |
| `frame-ancestors` | `'none'` | SecurityOS may not be embedded anywhere (anti-clickjacking). Backed up by `X-Frame-Options: DENY`. |
| `upgrade-insecure-requests` | — | Force any `http:` subresource to `https:`. |

**`Cross-Origin-Embedder-Policy` is intentionally OMITTED.** `require-corp`/
`credentialless` break the v86 `wss://` network relay and cross-origin images.
Only enable COEP if you later need `SharedArrayBuffer` *and* have verified every
cross-origin resource serves CORP/CORS.

## Apps disabled by the strict default (and how to re-enable)

Omitting `'unsafe-eval'` is deliberate — it's the highest-value XSS mitigation.
The trade-off: three Emscripten-compiled apps call `eval()` / `new Function()` at
runtime and therefore **do not work under the default policy**:

| App | Why it needs eval |
| --- | --- |
| **Pyodide** — Terminal `python`/`py` command | Emscripten `EM_JS` / `_emscripten_run_script` use `eval()` |
| **SpaceCadet** — 3D Pinball | Emscripten Embind `createNamedFunction` uses `new Function()` at module init |
| **Ruffle** — Flash player | Uses `new Function()` in its loader |

This is the correct posture for a security-focused OS. If you operate a private
instance and accept the weaker policy, re-enable them by building/serving with:

```sh
SECURITYOS_ALLOW_EVAL=1 yarn start          # or yarn deploy / yarn build:headers
```

That adds `'unsafe-eval'` to `script-src` everywhere (header, `public/_headers`,
and the `<meta>` fallback, since they share `scripts/securityHeaders.js`).
**Leave it unset on any public/hardened or `.onion` deployment.** Everything
else (Monaco, the WASM emulators, the SecTools suite, the in-OS Browser) works
fine under the strict default.

## Tightening further (optional, stricter privacy)

`connect-src`/`img-src`/`frame-src`/`media-src` use the broad `https:`/`wss:`
tokens so the in-OS Browser and a **user-chosen** Tor relay keep working. If you
run a locked-down instance where users cannot set their own endpoints, replace
those broad tokens with an explicit allowlist of only the hosts your build
actually contacts, e.g.:

```
connect-src 'self' blob: data: wss://relay.widgetry.org https://api.nasa.gov https://wttr.in https://gateway.ipfs.io;
```

See the egress inventory in the audit notes for the full host list. Also
consider adding a `report-to`/`report-uri` endpoint to collect CSP violations
before tightening.

## Verifying

```sh
# Node server
yarn start &                     # next build && next start (port 3000)
curl -sI http://localhost:3000/ | grep -iE 'content-security|strict-transport|x-frame|permissions-policy'

# Static export
yarn deploy                      # writes ./out  (+ regenerates public/_headers)
cat public/_headers
```

Then run the page through <https://securityheaders.com> and the CSP through
<https://csp-evaluator.withgoogle.com>.
